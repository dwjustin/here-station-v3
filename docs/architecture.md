# 구조

1. 앱이 역을 선택하고 API에서 지도 버전과 파일 주소를 받는다.
2. 앱이 지도 JSON과 필요한 표시용 GLB를 다운로드하고 기기에 보관한다.
3. 앱에서 출발 위치와 방향을 확인한다. 초기 위치를 얻는 방법은 추가로 설계한다.
4. 앱이 출발·도착 역 ID를 API에 보낸다.
5. 서버가 구간(역)마다 목적지에서 거꾸로 Dijkstra를 돌려 보행 칸 전부의 안내 방향을 반환한다.
6. 앱이 센서로 이동을 추정하고 지도와 맞춰 현재 위치와 AR 안내를 갱신한다.
7. 경로를 벗어나도 밟은 칸의 방향이 이미 있으므로 걷는 동안 서버를 다시 호출하지 않는다.

지도 JSON은 보행 데이터다. JSON을 얻는 것과 실제 현재 위치를 아는 것은 별도 작업이다. 초기 위치·방향 확인, 센서 오차, 지도·AR 좌표 관계를 각각 다뤄야 한다.

층별 PNG는 사용하지 않는다. 역사 형태를 그릴 경우 표시용 GLB 또는 보행 데이터 기반 렌더러가 필요하다. 원본 GLB를 앱에 항상 내려받을지는 화면 요구사항에 따라 결정한다.

현재 백엔드는 `/health`, Supabase의 `stations` 테이블을 조회하는 `GET /stations`, 홍제 → 잠원 칸별 안내 방향을 계산하는 `POST /routes`를 구현했다. Supabase에는 `stations`·`station_maps` 테이블과 외래 키가 있고 역 일곱 개가 등록되어 있다. 검색은 서버 전용 키로 역 정보만 조회하며 지도 데이터는 읽지 않는다. 경로 API는 출발·도착 역 ID를 받아 로컬 `data/maps/`(`MAP_DIR`)의 지도로 보행 칸마다 목적지 쪽 방위를 계산해 반환한다(그 외 조합은 `404`, 지도 파일이 없으면 `503`). 위치·방향 추정은 앱이 한다. 지도 파일 저장소(Supabase) 연결과 다른 역 조합은 후속 작업이다.
